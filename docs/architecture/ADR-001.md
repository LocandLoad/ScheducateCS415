# ADR-001: Use a Layered ASP.NET Core Architecture with Entity Framework Core

**Status:** Accepted

## Context

*Scheducate* is a one-semester course project. A small team will build the application incrementally throughout the course.

The system needs to support user accounts, schedules, availability, groups, group memberships, invitations, and shared schedules. It also needs persistent storage for this information.

Scheducate is built using ASP.NET Core. The application uses ASP.NET Identity for user authentication and Entity Framework Core for communication with the database.

We need an architecture that is simple enough for a small team to develop and maintain while keeping the application's user interface, application logic, and data access responsibilities separated.

## Decision

*Scheducate* will use a **layered ASP.NET Core architecture**.

The application will be organized into the following major layers:

- **Presentation layer:** ASP.NET Core MVC controllers and views responsible for handling HTTP requests and presenting information to users.

- **Application/logic layer:** Application logic responsible for operations such as creating schedules, managing groups, processing invitations, and determining shared availability.

- **Data access layer:** Entity Framework Core and `ApplicationDbContext` responsible for accessing and modifying persistent data.

- **Database:** A relational database used to store users, schedules, groups, memberships, invitations, and other application data.

ASP.NET Identity will be used for authentication and user management. Identity will manage user credentials and authentication-related data rather than Scheducate implementing password storage and authentication manually.

Entity Framework Core migrations will be used to create and update the database schema.

The application will support SQL Server on Windows and SQLite on other supported platforms through the database configuration in `Program.cs`.

## Alternatives Considered

### Three-Tier Client-Server Architecture with a Separate Frontend

Rejected as the primary architecture because Scheducate is currently implemented as an ASP.NET Core application rather than as a separate frontend and backend.

A separate React or other JavaScript frontend would introduce an additional application and API boundary that is not necessary for the current project requirements.

### Microservices

Rejected because they would add unnecessary complexity for a one-semester project.

Scheducate does not currently require independently deployed services, independent scaling, or the operational complexity associated with multiple services.

A single application is easier for the team to develop, test, and deploy.

### Direct Database Access from Controllers

Rejected because controllers should not contain all database access logic.

Keeping database operations within the Entity Framework Core data-access layer makes the application easier to organize and maintain.

It also reduces duplication when multiple features need to access the same data.

### No Architectural Separation

Rejected because putting presentation, application logic, and database operations together would make the system harder to maintain as more features are added.

Scheducate contains multiple related features, including schedules, groups, invitations, and shared availability. Separating responsibilities makes these features easier to modify independently.

## Consequences

### Positive

- Keeps presentation, application logic, and data access responsibilities separated.
- Makes the application easier for a small team to understand and maintain.
- Allows new features to be added without putting all application logic into controllers.
- Entity Framework Core provides a consistent way to work with the application's relational data.
- ASP.NET Identity provides established authentication and user-management functionality.
- Database migrations make changes to the database schema easier to manage.
- The architecture is simple enough for the scope of a one-semester project.

### Negative

- The application remains a single deployment.
- A failure in the ASP.NET Core application can make multiple features unavailable at the same time.
- Additional abstraction between controllers and data access can require more files and code for simple operations.
- Supporting both SQL Server and SQLite can require additional testing to ensure that database behavior remains consistent.

These trade-offs are acceptable for the current scope of Scheducate. The architecture can be reconsidered if the application's requirements grow significantly.
